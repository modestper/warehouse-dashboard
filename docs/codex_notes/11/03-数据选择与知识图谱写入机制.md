- `--kg-state-source memory` 表示派单从内存取状态，不表示不写图谱；是否写图谱仍由独立写入开关控制。

#### 3. 静态图谱与运行态图谱

静态导入由 `scripts/import_warehouse_neo4j.py` 处理地图和固定任务，写 Warehouse、Zone、Rack、Location、Dataset、Goods、WarehouseTask 及其关系。默认离线检查，显式 `--apply` 才连接写库；通常在数据准备时执行，不随每个仿真步重新导入。

运行启动创建 Run，利用 `graph_dataset_id` 将 Run 与既有 Dataset、Execution 与既有 WarehouseTask 关联。因此要建立完整静态关联，配对的静态数据需先存在。

运行态有三种主要情况：

| 路径 | 机器人状态 | 全局事实 | 本地持久化 |
|---|---|---|---|
| 普通 journal，无图谱开关 | 内存推进，无运行态 Neo4j 写入 | 不自动写 Neo4j | 默认每 5 仿真秒保存，另有强制边界 |
| 旧 `--ray --robot-graph` | 每 tick 提交快照，历史 AgentState 默认每 4 tick/tick 1 写入；没有新路径的逐步完整 current_robot 发布 | 旧 `--global-writer` 在本地保存点提交；可选 HTTP 路径需看对应参数 | 同上 |
| 新 `--robot-processes ray --robot-graph --global-writer-url URL` | 每 tick 发布完整当前 Robot 状态，历史 AgentState 默认每 4 tick/tick 1 写入，事件按实际发生记录 | 每 tick 统计、事件与 Step；DispatchState 每 5 tick | 同上 |

运行时一个物理 step 推进一仿真秒；倍速只是改变墙钟推进速度。这里的 4/5 tick 不应理解为固定 4/5 秒实际等待时间。

#### 4. 新路径每步写入的细节

1. 主进程派单，100 个有状态 Ray actor 推进各自机器人，主进程获取本步结果。
2. 保存该 tick 的不可变机器人快照与新事件。
3. 每个 actor 用自身 Neo4j writer 写自己的历史/事件，再更新 Robot 上的完整当前状态 JSON `payload`、`last_written_tick` 以及位置、电量等字段。
4. 完整当前状态是更新现有 Robot 节点，不是每秒新增一套完整 Robot 历史；历史 AgentState 在 `tick % graph_state_interval == 0 or tick == 1` 时才新增。
5. Execution/ExecutionState 根据采样状态或实际事件生成；RuntimeEvent 由实际事件产生，不是每步伪造一个业务事件。
6. 收齐 100 台机器人实际写入成功的回执后，主进程经 HTTP 向全局服务提交本步 RunStat、Assist/Handoff、所有权变更和全局事件等。
7. 全局服务完成这些写入后，写完整 `Step` 并在同一条 Cypher 事务中单调推进 `Run.latest_step`。各机器人/全局事实并不是共享一个巨型原子事务；Step 是完整可用的发布边界。

异步生效条件为 `memory + robot-processes ray + robot-graph + global-writer-url`，且未使用 `--robot-graph-sync`。默认队列上限 120 帧，范围 1～128。主循环允许先推进若干步，后台按 FIFO 处理写入；HTTP 202 只代表服务接收，不等于写入完成。只有确认数据库 `latest_step >= tick` 才完成该帧。队满时在新物理步开始前等待，发生写入失败时暂停相应路径。

`--kg-state-source neo4j` 是同步一致性对照，每轮等图谱完整状态；`memory` 使用 actor 的内存返回值派单。二者的取数选择与是否启用图谱写入是不同维度。
