# 仓储物流机器人操作上下文查询方案（待评审）

### 任务背景

用户希望参考 LaDe 机器人决策上下文查询的特点，为当前仓储物流机器人设计与实际操作关联的查询语句，并要求先提出大体方案评审。本轮只检查源码并整理设计，没有生成或接入新的可执行查询，没有运行压测或访问数据库。

默认范围是当前 V5 仓储仿真，兼容 medium 轮式混合机队与旧版 all-X3 输入；实际型号、地图、阈值均来自当前 run，不根据页面名称或过去某次启动参数猜测。

### 关键结论

- 建议采用“操作触发 → 读取同一时刻上下文 → 形成候选与拒绝理由 → 中央运行器最终验证”的方式组织查询。
- 规划8类操作上下文包、首版目标24条查询；数量服从真实操作需要，不为凑齐 LaDe 的56条而添加无用途查询。
- 每条查询必须说明使用者、触发时机、需要回答的问题、参数、真实数据来源、返回字段及缺失信息；仅返回节点数量或全仓统计的查询不算机器人操作决策查询。
- 复用已有 `Run/Robot/AgentState/RuntimeEvent/ExecutionState/OwnershipChange/Handoff/DispatchState` 和静态 `Dataset/WarehouseTask/Location/Rack`，避免照搬 LaDe 的 `Drone/Task/OF_DRONE` 标签。
- 当前图谱可以提供自身采样、任务静态要求、执行和交接证据等事实；实时库存、完整故障状态、路线/能源结果和电池资源并未全部成为可直接查询的时序图谱事实，必须明确缺项或补充运行摘要。
- 当前 actor 的上下文查询结果只用于观测，不参与选单。新目录先做场景验证与对照，再决定是否把上下文结果送到既有决策入口，不在本轮改变派单与安全规则。

#### 1. 参考 LaDe 的哪些特点

1. 以单台机器人为中心，统一使用 `run_id`、`robot_id` 和截止 `tick`，避免跨实验或读取未来信息。
2. 根据机器人正在考虑的操作组织查询包，而不是把所有查询一次性全部执行。
3. 读取自身状态、任务条件、历史证据、同伴状态和资源约束，给出可解释的决策依据。
4. 区分“当前属性”“截止某步的采样”“事件窗口”，输出真实观测时间与陈旧度。
5. 把一组决策上下文视为一次完整请求，分别计量整包时延和内部单条查询时延。

#### 2. 操作查询目录草案

以下是待设计的业务查询，不代表当前24项已经能由图谱独立完整回答。每包中标明的运行缺项，需要先补足来源再实现对应操作判断。

| 查询包 / 使用者 | 计划查询 | 使用时机及实际用途 |
|---|---|---|
| 自身就绪 / 机器人、中央 | W01 完整步锚点与新鲜度；W02 当前任务/载货/阶段；W03 型号能力与有效配置 | 接单、求助或恢复前，确认读取的状态有效，自己正在做什么、具备什么操作能力 |
| 接单与衔接 / 中央调度 | W04 已释放候选任务；W05 当前任务责任与重复派发检查；W06 源/目标货位能力匹配 | 空闲或卸货/补能后考虑下一单；排除未来任务、能力不足及已有有效负责人冲突 |
| 取货与放货 / 中央业务标记 | W07 取货货物身份与源位置证据；W08 目标货位占用/预约；W09 取放阶段及已完成动作 | 进入取货、放置前核对货物、货位与动作阶段，避免拿错货、重复取货或重复入库 |
| 移动与等待 / 中央规划 | W10 当前执行段与目标；W11 附近机器人及等待证据；W12 阻塞原因与受影响对象 | 出发、长时间等待或恢复时定位目标和原因，为已有路线规划器提供上下文 |
| 补能 / 中央补能调度 | W13 自身电量与任务阶段；W14 任务后续及补能能源评估；W15 充电位/换电资源候选 | 判断继续任务、先充电或换电的输入条件；比较补能资源候选 |
| 请求接力 / 持货机器人、中央 | W16 求助触发与既有协助；W17 剩余目标能力；W18 接收者候选 | 已取货后收到低电反馈、故障或显式交接请求，寻找能继续完成剩余任务的机器人 |
| 接应接力 / 帮手机器人、中央 | W19 自身是否已有任务/载货/故障；W20 交接双方、货物与任务责任；W21 接应/交付/补能评估 | 接受帮忙或实际交接前，防止重复接应、货物归属冲突和接手后无法完成任务 |
| 故障与恢复 / 中央恢复流程 | W22 故障及进展事件；W23 已取/已放/已交接历史证据；W24 当前责任与恢复检查清单 | 恢复配送、交接失败后重规划时，保留已完成动作及唯一货物负责人 |

“接单”“资源预约”“路线选择”的使用者主要仍是中央，不能将这些查询包描述为 actor 已经可以自行领单或自主规划。

#### 3. 现有数据能支持到什么程度

| 数据来源 | 当前实际可读取内容 | 需要保留的限制 |
|---|---|---|
| `Run.latest_step`、`Step` | 最近完整提交步、接收机器人数量与完成标记 | 完整Step不等于100台都有当步历史采样；还需检查各机器人观测时间 |
| `AgentState` | stage、battery、x/y、task_id、cargo_id、tick | 状态受采样频率与 `record_agent_state` 开关影响；缺历史不能当作空闲 |
| `Robot` | 运行内身份、type；最新 `payload` 与 `last_written_tick` | type可以作为运行内稳定属性；可变payload必须校验精确版本，不用它回答过去时刻状态 |
| `WarehouseTask/Location/Rack` | 任务类型、货物、源目标、释放/截止时间、货层、位置及布局事实 | 静态任务可能尚未释放；逻辑 `INBOUND/OUTBOUND` 不等于运行中已绑定的物理工位 |
| `ExecutionState/RuntimeEvent/OwnershipChange/Handoff` | 任务采样、动作事件、负责人变更与实际交接证据 | 不把历史 `ASSIGNED_TO` 参与者当成唯一当前负责人；重入队、取消和缺失记录需单独识别 |
| `DispatchState` | 活跃job摘要、最多前200条pending、口内数量等JSON字段 | 有截断、有提交间隔；pending不等于全部任务，更不等于已经通过库存和路线门禁的可派任务 |
| `Assist` | 已记录协助对象、任务和交接时间 | 状态会变化，历史查询不能直接读取今天的active/ended值冒充过去状态；截止时刻覆盖不足就报缺 |
| 运行配置及能力代码 | 三型号能力、货位高度规则、补能和储备阈值 | 规则目前主要在代码与配置；查询返回事实后复用同一能力函数计算，不伪造不存在的图谱属性 |

需要补充的真实运行资料重点为：货位实时占用和预约、货物当前持有者、逐机器人故障/可衔接状态、当前任务执行段摘要、充电位可用时间、换电电池可用库存及预约、现有规划器计算的路线耗能与拒绝原因。

建议通过已有中央/机器人写者投影最小必要摘要，并带 `run_id/tick`，不新造与真实仿真状态分离的第二套库存或预约。具体是否补字段、还是先通过只读运行接口返回，需在本方案通过后按查询逐项决定。

即使Neo4j恢复检查点JSON包含部分资料，也不建议每台机器人每次决策都读取和解析完整100机器人检查点；常规查询应读取对应的有界事实。

#### 4. 四个操作例子

**A1 接第3层入库任务。** 查询返回当前型号A1、源口、目标第3层及有效配置；复用 `task_capability_reason()` 得到 `capability_level`。该组合不进入实际派单。不能因为A1离入库口近就忽略目标能力。

**X3 已从第3层取下出库货物，收到24%电量反馈。** W16读取真实反馈与当前持货事实，W17确认剩余目标为地面出库口，W18可将满足其他条件的A1列为候选。最终仍需现有 `request_assistance()` 验证会合、交接、配送和后续补能路径，查询不直接宣布“安全交接”。

**X3 持有尚须放到第3层的入库货物。** 接力接收者必须有第3层放置能力；A1/R2被排除。不能只按距离与电量筛帮手。

**机器人刚换完电、准备衔接下一单。** 查询要核对补能完成事件、当前电量、载货状态、中央可衔接标记及候选任务释放状态；确认候选事实后仍由 `release_and_dispatch()`、`schedule_task()` 提交实际新计划，不要求先返回待命点。

#### 5. 统一时间与输出合同

- 每次请求只确定一次完整步t，所有历史事实使用 `tick <= t`；实际运行中1tick目前对应1秒仿真时间，仍显式标注单位。
- 返回 `run_id/dataset_id/robot_id/requested_tick/observed_tick/age_ticks`，并附带每类事实的来源与缺失项。不同采样时间不能包装成同时发生的精确状态。
- `DispatchState` 另返回其 `observed_tick/pending_count/returned_count/truncated`；不能用截断的队列证明“全场没有更多任务”。
- 静态ISO释放时间按当前Dataset.start归一化为仿真时间。候选任务必须已经在运行中发布；对机器人不可见的未来订单不进入决策上下文。
- JSON形式事实由统一上下文组装层解析，避免要求不存在的APOC插件；不能把序列化字符串当成已索引结构化属性使用。
- 查询结果包含事实、可证明的候选/排除理由、`missing`和`requires_validation`。未查询到或覆盖不足返回未知，不补0、不推断为空闲/空货位。
- 最终路线碰撞、能源准入、货位预约、交接原子性继续复用SIPP、`_energy_admission()`、库存检查及`transfer_custody()`等实际代码。

#### 6. 如何判断方案有效

建议先选8～12条覆盖核心操作链的查询实现并验证，再扩成24条；先不接管实时调度。

1. 对照同一仿真快照：任务、货物、型号、电量、负责人和时间口径与主进程事实一致。
2. 场景验证：低层正常入出库、A1高层拒绝、未释放任务隔离、两种不同方向的高层接力、换电无可用电池、任务重新入队、故障后恢复不重复取货。
3. 记录不全验证：无AgentState历史、过旧采样、未完整Step、图谱未记录库存时，返回缺项而不是错误许可。
4. 组包效率验证：相同机器人同一tick共享自身状态/配置/事件，按动作读取所需包，不每次执行24条全量查询。
5. 并发验证：逐步增加到100机器人，记录整包端到端平均/P95/P99、错误与缺项率、返回条数、图谱规模及持续写入情况。没有实际测试前不承诺500ms。
