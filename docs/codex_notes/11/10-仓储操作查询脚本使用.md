# 仓储操作上下文查询脚本

入口：[scripts/warehouse_llm_context_queries.py](../../../scripts/warehouse_llm_context_queries.py)。当前 V3 的14条具体 Cypher 位于 [config/warehouse-context-queries.json](../../../config/warehouse-context-queries.json)，读取和结果处理位于 [backend/robot_operation_context.py](../../../backend/robot_operation_context.py)。[V2扩充说明](11-操作查询扩充与用途.md)记录查询用途；[V3修订](11-查询解除Dataset强制依赖.md)解除 Dataset 强制依赖，三个并发入口共用此逻辑。已完成实库编译、单机器人读取和事务回滚样例验证。

## 直接运行

在仓库根目录执行，将 `test_110404` 换成实际存在且已写入完成 Step 的 runId：

```bash
./run_in_lade.sh python scripts/warehouse_llm_context_queries.py \
  --run-id test_110404 --robot-id 1 --queries all --print-context
```

连接参数优先级：命令行 > `NEO4J_*` > `WAREHOUSE_NEO4J_*` > 项目默认值。默认连接 `bolt://127.0.0.1:47687`、用户 `neo4j`、数据库 `neo4j`。密码从环境读取；交互终端缺少密码时会提示输入。非交互环境需要预先设置密码，否则退出码2，不尝试连接。

```bash
export NEO4J_URI='bolt://127.0.0.1:47687'
export NEO4J_DATABASE='neo4j'
# 使用现有 NEO4J_PASSWORD / WAREHOUSE_NEO4J_PASSWORD，或在终端提示中输入。
```

同样可用 `--uri`、`--user`、`--database`、`--password` 指定。查询日志不记录连接密码。

## 查询编号与选择方式

| 编号 | 名称 | 业务用途 |
|---|---|---|
| `w0` | `basis` | 完成步、本机状态、型号、配置及新鲜度，附可选数据集元信息 |
| `w1` | `task_pool` | 已观察候选队列、活动作业和工位件数摘要 |
| `w2` | `task_geometry` | 指定任务的取放位置、物理工位绑定、机械臂能力与期限 |
| `w3` | `task_evidence` | 任务执行样本、责任变更、已发生交接和操作事件 |
| `w4` | `peer_states` | 同伴状态、直线距离排序提示和潜在接收者 |
| `w5` | `self_feedback` | 本机窗口内状态与事件、观察到的电量和位置变化 |
| `w6` | `task_timing` | 指定任务的阶段耗时、重新排队和执行轮次证据 |
| `w7` | `cargo_history` | 同一货物跨任务的事件、交接与最新持有样本 |
| `w8` | `progress_summary` | 整个窗口的空间、电量、阶段和采样统计 |
| `w9` | `completion_feedback` | 本机最近完成任务及相对截止时间的反馈 |
| `w10` | `recovery_markers` | t之前各类最后停机/恢复记录，包含短窗口外证据 |
| `w11` | `handoff_outcomes` | 本机参与接力后的执行与完成证据 |
| `w12` | `rack_workload` | 已观察主任务按货架聚合的作业引用 |
| `w13` | `port_pressure_history` | 多份快照中实际记录的工位件数变化 |

```bash
# 不连接数据库：查看目录或打印14条语句及参数解析规则。
./run_in_lade.sh python scripts/warehouse_llm_context_queries.py --list-queries
./run_in_lade.sh python scripts/warehouse_llm_context_queries.py \
  --run-id test_110404 --queries w0-w13 --dry-run

# 先在目标库编译所选语句，不读取业务结果。
./run_in_lade.sh python scripts/warehouse_llm_context_queries.py \
  --run-id test_110404 --queries all --explain

# 读取某个任务定义和取放要求，自动追加 w0；显式任务不再读取候选池。
./run_in_lade.sh python scripts/warehouse_llm_context_queries.py \
  --run-id test_110404 --robot-id 1 --queries task_geometry \
  --task-id V3-T-0000015 --print-context
```

支持逗号组合、编号范围、语义名称和类别，例如 `--queries w2,w3`、`--queries self,history`、`--queries w6-w13`。选择会去重，并按数字编号的依赖顺序执行。没有显式任务而需要 `w2/w3/w6/w7` 时，优先取本机任务；本机也没有任务时自动读 `w1` 的候选队列。候选须已释放、快照未超过容忍度且未被快照中的活动作业占用；默认最多8个任务，通过 `--max-tasks` 调整，最大32。显式任务超过上限时直接报参数错误，不静默丢弃。

常用操作包：`core=w0,w5`，`task_decision=w0,w1,w2,w3,w6,w12`，`task_execution=w0,w2,w3,w6,w7,w10`，`request_help/provide_help=w0,w2,w3,w4,w7,w11`，`energy_safety=w0,w5,w8,w10`，`recovery=w0,w3,w7,w8,w10`，`all=w0-w13`。另有 `task_progress / memory_review / local_awareness / data_readiness`，通过 `--list-queries` 查看组成。默认执行 `core`。这些包只读取上下文，不会认领任务、创建协助承诺或下发控制指令。

“14条”指14种参数化查询语句，不代表每次恰好发送14次查询：依赖会自动补齐；没有已观察任务时 `w2/w3/w6/w7` 明确记录 `skipped:no_observed_task_ids`；自动追加的候选池在已有本机任务时也会跳过。

## 指定时间与并发测试

```bash
# 所有 context 使用显式完成步100，10个并发，每台重复3次。
# --output-dir 必须尚不存在，避免覆盖已有日志。
./run_in_lade.sh python scripts/warehouse_llm_context_queries.py \
  --run-id test_110404 --tick 100 --robot-ids 1-100 \
  --queries task_decision --max-workers 10 --repeat 3 \
  --output-dir /tmp/warehouse-context-test-001
```

不填 `--tick` 时，每个 context 分别读取一次 `Run.latest_step`；运行继续推进时，不同机器人可能锚定不同步。要比较同一逻辑步，须显式指定一个已经发布的 `--tick`。事务逻辑与 LaDe 查询脚本一致：同一个 context 复用一个只读会话，通过 `session.run()` 逐条执行，每条使用独立的自动提交事务；完整消费结果后再执行下一条。不同 context 并发，同一 context 的查询按依赖顺序执行。所有语句复用首次取得的时间和 runId 边界；自动提交不提供跨查询的统一历史快照。

`--transaction-timeout` 默认30秒，作用于每条查询的自动提交事务，不再是整个 context 的事务总时限。结果和逐条日志中的 `transaction_mode=auto_commit_per_query` 标明当前执行方式。

缺 Run、缺完成 Step、完成步不匹配时，记录 `unavailable` 并停止后续查询。Dataset 节点或关联缺失不再阻止查询；运行状态、队列、事件和执行证据直接按 runId 与时间范围读取。静态定义优先沿当前 run 的 `Execution-[:EXECUTES]->WarehouseTask` 查找，否则使用运行声明的唯一数据集标识匹配任务属性；不会只凭 task_id 跨数据集查找。标识冲突只禁用该静态回退并标明告警，不阻止运行查询。缺本人采样、数据陈旧、JSON 缺失、货架或期限背景缺失等可产生 `incomplete`；有合法时间锚点时仍可返回其他观察信息。脚本不会创建 Run、导入静态数据或启动仿真。

容忍度和展示上限可以调整，例如：

```bash
./run_in_lade.sh python scripts/warehouse_llm_context_queries.py \
  --run-id test_110404 --tick 100 --queries recovery \
  --history-ticks 80 --param max_state_age_ticks=0 \
  --param event_fetch_limit=101 --include-cypher
```

可覆盖参数：`max_state_age_ticks`（默认4）、`max_peer_age_ticks`（4）、`max_snapshot_age_ticks`（5）、`binding_fetch_limit`（17）、`evidence_fetch_limit`（17）、`state_fetch_limit`（65）、`event_fetch_limit`（33）、`result_fetch_limit`（17）、`from_tick`。这些默认数是读取策略，不是仿真业务常量。`*_fetch_limit` 是“展示条数+1”，范围2～1001；多取的一条用于报告截断，不进入展示结果。任务列表、时间锚点、机器人和数据集不能通过 `--param` 绕过解析规则覆盖。

## 输出和边界

默认输出到当前工作目录的 `data/warehouse_context_queries/时间戳-随机后缀/`，也可指定全新 `--output-dir`：

- `contexts.jsonl`：每个机器人每次 context 的查询结果、派生事实、缺项、截断和状态。包括 `run_id/robot_id/requested_tick/tick/dataset_id/context_index`，以及 `action_authorized=false`。
- `queries.jsonl`：逐条执行或跳过记录，含实际参数、耗时、服务端返回/消费耗时、行数和错误；`--include-cypher` 时附具体语句。执行或提交失败会标为 `error`，继续尝试后续查询，不会把整个 context 的剩余查询统一跳过。若 `w0` 失败导致没有有效时间锚点，后续查询仍因 `anchor_unavailable` 跳过；候选发现失败且没有可用任务 ID 时，只跳过缺少任务输入的查询，其他查询继续。
- `summary.json`：context 数和状态、实际执行/跳过/失败次数、每条查询均值/P50/P95/最大耗时与行数，以及整批墙钟耗时。跳过记录不进入查询耗时分位数。

逐条 `elapsed_ms` 包含 `run`、完整取结果和 `consume`，以及该条语句的自动提交开销；context 的 `elapsed_ms` 包含语句执行及结果组装，`worker_elapsed_ms` 另包含会话建立和关闭等开销，`queue_ms` 是线程池排队时间。整批墙钟耗时也包含结果文件写入。日志按完成顺序写入，用 `context_index` 关联，不按行顺序推断机器人先后。

退出码：0表示批次正常完成（可能含明确标记的观测缺项）；1表示连接/查询失败或存在 `unavailable` context；2表示参数或凭据缺失。打印原始结果可用 `--print-context`。

当前保留的限制：库存、货位/道路预约、完整故障与空载信息、补能资源和助手承诺尚未完整入当前 C 图；候选不是可领取任务，潜在接收者不是已承诺助手，直线距离不是 SIPP 路线。当前静态包中的货架引用问题会导致 `source_rack/target_rack` 缺失，脚本返回能力未知或已有硬性不满足原因，不把缺失伸展要求当成0。历史配置/布局/写入 epoch 尚无统一版本校验，结果标记 `bounded_history_writer_epoch_unverified`。
