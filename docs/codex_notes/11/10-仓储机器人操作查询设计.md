# 仓储机器人操作查询设计

本文记录 V1 的六条基础查询：一个公共依据、五个业务读取。它们面向 `Run / Dataset / AgentState / DispatchState / WarehouseTask / ExecutionState / RuntimeEvent / OwnershipChange / Handoff` 图模型。当前 V2 已扩充为[14条具体查询](11-操作查询扩充与用途.md)，原六条编号保持兼容。

查询已提供[脚本执行入口及使用说明](10-仓储操作查询脚本使用.md)，当前运行目录为 `config/warehouse-context-queries.json`（编号 w0～w13），尚未接管机器人决策或修改中央调度。本文 V1 Cypher 和示例参数另存于[设计参考 JSON](10-仓储机器人操作查询目录.json)。示例 `YOUR_RUN_ID / ANCHOR_DATASET_ID / KNOWN_TASK_ID` 必须替换为本次查询实际取得的值；其他数值也只是参数示例。

## 每条为什么需要

| 模板 | 帮助决定什么 | 删除后会缺什么 |
|---|---|---|
| `basis` | 现在是否有足够基础观测继续判断 | 统一时间锚点、本人状态、型号、运行配置和数据新鲜度 |
| `task_pool` | 空闲时先评估哪些任务 | 实际已观察队列；否则会把全天静态任务误作可领取任务 |
| `task_geometry` | 去哪里取放、机械臂是否满足剩余操作 | 货层与伸展要求、逻辑工位解析、任务期限 |
| `task_evidence` | 任务进展、责任和交接是否已有证据 | 取放反馈、重新排队、重复接单与责任冲突判断依据 |
| `peer_states` | 谁可能接力、附近有哪些已观察同伴 | 同伴位置、状态、电量、型号与观测缺项 |
| `self_feedback` | 执行后是否有进展、是否需要恢复判断 | 近期变化、动作事件、等待与电量变化的证据 |

“读状态”和“查反馈”不合并：前者每次决策都需要，后者只在反馈/恢复时读窗口，避免每次拉历史。“任务定义”和“执行证据”不合并：定义可按数据集缓存，执行证据必须按本次时间刷新。没有单列“低电机器人/高层任务/附近机器人”等只改过滤条件的重复模板。

## 时间、返回值和组装约定

1. 先执行 `basis`，固定 `run_id/t/dataset_id/step.elapsed`，同一决策的其余读取统一使用这些值。`tick` 是逻辑步；任务释放与截止、规划持续时间使用运行秒，不能默认二者永远相同。
2. 历史读取只用 `tick <= t` 的状态/事件和稳定元数据。`Run.config_json`、布局与机器人型号没有历史版本：历史查询成立的前提是一个 Run 内配置、布局、数据集和型号不变；不能复用同一 runId 重置时间线后声称旧历史仍可靠。换配置/回放重建要用独立 Run 或增加版本。
3. 完成 Step 只是写入协议边界，不等于所有类型都有每步样本，也不是 Neo4j 自动的时间旅行快照。当前执行脚本与 LaDe 一样，在同一只读会话中逐条使用自动提交事务，全部语句复用首次取得的时间锚点；仍要求写者不再回填/覆盖已发布边界。这不提供跨查询的统一历史快照，脚本结果标记 `bounded_history_writer_epoch_unverified`。
4. 结果统一包含 `query_status / requested_tick / observed_tick / age_ticks / missing_fields / truncated / scope`。`not_observed`、确实观察到空集合、查询失败、数据陈旧必须区分。模板返回原始事实；组装器负责 JSON 解析、单位换算、证据冲突、派生指标及解释。
5. 列表采用 `展示上限+1` 读取后标记截断；任务列表参数去重、限长，窗口参数及 LIMIT 必须为正整数，`0 <= from_tick < t`，历史 `t` 非负；阈值须有限且来自明确策略。没有状态时不能自动填 `idle/100%/空载`。
6. 查询只读，不包含认领、预约或操作指令。即便候选通过全部观测检查，执行前仍需在当前权威状态上原子认领任务、验证货物持有/库存和预约资源。两个机器人同时读到同一候选是正常并发情况，必须由认领协议解决。

布局缓存及完整 Run 配置能减少重复读取；`task_pool`、机队状态可在同一锚点内共享。JSON 目录中的语句是模板，不是现有 `query_c` 已经提供的业务能力。

## 具体语句

### `basis`：本次决策依据

回答：我在什么运行、什么完成步上决策？自己的观测是否可用？

触发：每次新决策首先执行一次，其他查询复用返回的 t、dataset_id、step.elapsed。

参数示例：

```json
{
  "run_id": "YOUR_RUN_ID",
  "robot_id": 1,
  "at_tick": null,
  "max_state_age_ticks": 4
}
```

```cypher
MATCH (run:Run {id: $run_id})
WITH run, coalesce($at_tick, run.latest_step) AS t
OPTIONAL MATCH (step:Step {run_id: $run_id, tick: t})
WITH run, t, collect(step) AS steps
CALL {
  WITH run
  OPTIONAL MATCH (run)-[:USES_DATASET]->(dataset:Dataset)
  RETURN collect(DISTINCT dataset{.id, .start, .time_unit, .warehouse_id}) AS datasets
}
CALL {
  WITH run, t
  OPTIONAL MATCH (robot:Robot {id: $run_id + ':robot:' + toString($robot_id), run_id: $run_id})
  OPTIONAL MATCH (state:AgentState {run_id: $run_id, robot_node_id: robot.id})
  WHERE state.tick <= t
  WITH robot, state ORDER BY state.tick DESC, state.id DESC LIMIT 1
  RETURN robot.type AS robot_type,
         state{.tick, .stage, .battery, .x, .y, .task_id, .cargo_id} AS self_state
}
RETURN run.id AS run_id, t, run.latest_step AS published_tick,
       size(steps) AS step_count,
       CASE WHEN size(steps) = 1 THEN properties(steps[0]) ELSE null END AS step,
       datasets, robot_type, self_state,
       t - self_state.tick AS state_age_ticks,
       run.config_json AS config_json,
       run.scene_sha256 AS scene_sha256, run.tasks_sha256 AS tasks_sha256,
       CASE WHEN size(steps) = 1 AND steps[0].complete = true
                 AND steps[0].received_robot_count >= steps[0].expected_robot_count
                 AND steps[0].expected_robot_count > 0
                 AND t <= run.latest_step
                 AND size(datasets) = 1 AND robot_type IS NOT NULL
                 AND self_state IS NOT NULL AND t - self_state.tick <= $max_state_age_ticks
            THEN true ELSE false END AS observation_ready
```

**存在理由：**没有统一的时间锚点，后面的“我空闲、任务待领、同伴空闲”可能来自不同时间；缺状态也可能被误判成空闲。

- `at_tick=null` 表示固定读取一次 `Run.latest_step`，显式历史 tick 必须有对应完成步，不能自动跳到别的时间。
- `datasets` 必须恰好一个；后续 `$dataset_id` 来自这里，不能填前端显示名 `medium19` 代替图谱完整 ID。
- `max_state_age_ticks=4` 仅为示例容忍度，不是当前系统统一常量。取货、放货、交接等动作前还要取得当前执行器的即时状态。
- `observation_ready` 只说明基础观测满足上述条件。还必须检查必要字段非空、SOC 在 `[0,100]`、坐标有限、配置可解析；它不是动作授权。
- 查不到 Run 返回零行；查到 Run 但缺 Step/状态会显式返回缺项。`Robot.type` 只作为运行内稳定型号读取，不读取其可变的电量、任务或阶段作为历史状态。

### `task_pool`：已观察到的候选任务池

回答：我空闲时，有哪些已释放的任务值得进一步评估？

触发：机器人准备接新任务，或上一批候选失效时；同一运行和时间锚点可共享一次读取。

参数示例：

```json
{
  "run_id": "YOUR_RUN_ID",
  "dataset_id": "ANCHOR_DATASET_ID",
  "t": 100,
  "max_snapshot_age_ticks": 5
}
```

```cypher
MATCH (:Run {id: $run_id})-[:USES_DATASET]->(:Dataset {id: $dataset_id})
OPTIONAL MATCH (snapshot:DispatchState {run_id: $run_id, dataset_id: $dataset_id})
WHERE snapshot.tick <= $t
WITH snapshot ORDER BY snapshot.tick DESC, snapshot.commit_seq DESC LIMIT 1
RETURN snapshot IS NOT NULL AS has_snapshot,
       snapshot.tick AS observed_tick, $t - snapshot.tick AS age_ticks,
       CASE WHEN snapshot IS NOT NULL AND $t - snapshot.tick <= $max_snapshot_age_ticks
            THEN true ELSE false END AS snapshot_fresh,
       snapshot.elapsed AS snapshot_elapsed,
       snapshot.pending_json AS pending_json,
       snapshot.active_jobs_json AS active_jobs_json,
       snapshot.tasks_json AS tasks_json,
       snapshot.ports_json AS ports_json,
       'bounded_queue_total_unknown' AS completeness
```

**存在理由：**静态 `WarehouseTask` 包含整天的未来任务，不能把它们全部当成当前可领取任务。此查询提供运行中实际观察到的队列。

组装器解析 JSON，先保留 `waiting/accepted` 且 `release_second <= basis.step.elapsed` 的条目，再结合 `active_jobs`、`task_evidence` 排除已观察到的占用。返回的是“进一步评估候选”，不是已认领任务，也不是完整的库存就绪队列。保留拒绝原因，例如 `not_released / observed_assigned / stale_snapshot`。

`pending_json` 写入前最多取原队列前200条；落库节点没有 `pending_count`，不能准确知道遗漏多少。200条时标记“可能截断”；不足200条也不证明任务池实时完整。没有快照、快照陈旧、JSON 损坏、确实观察到空队列，必须分开表示。快照时间容忍度由决策策略指定，示例5不是写者频率保证。

`active_jobs_json` 不是完整道路预约；`ports_json` 是件数汇总，不能据此宣称某货位或工位已为本机保留。若计划挑选未绑定逻辑边界任务，物理工位须另由实际工位选择逻辑确定并原子确认。

### `task_geometry`：指定任务的取放要求与物理目标

回答：这个任务到哪里取、到哪里放？我的机械臂能完成剩余操作吗？

触发：评估 task_pool 中的任务、执行本机任务、评估某次接力时；任务定义和布局按版本缓存，边界绑定仍按 t 读取。

参数示例：

```json
{
  "run_id": "YOUR_RUN_ID",
  "dataset_id": "ANCHOR_DATASET_ID",
  "t": 100,
  "task_ids": [
    "KNOWN_TASK_ID"
  ],
  "binding_fetch_limit": 17
}
```

```cypher
MATCH (:Run {id: $run_id})-[:USES_DATASET]->(dataset:Dataset {id: $dataset_id})
      -[:USES_LAYOUT]->(warehouse:Warehouse)
CALL {
  WITH warehouse
  MATCH (warehouse)-[:HAS_LOCATION]->(port:Location)
  WHERE port.kind IN ['inbound', 'outbound']
  RETURN collect(port{.location_id, .kind, .x, .y}) AS physical_ports
}
UNWIND $task_ids AS requested_task_id
OPTIONAL MATCH (dataset)-[:INCLUDES_TASK]->(task:WarehouseTask {task_id: requested_task_id})
OPTIONAL MATCH (task)-[:CONCERNS]->(goods:Goods)
OPTIONAL MATCH (task)-[:FROM]->(source:Location)
OPTIONAL MATCH (task)-[:TO]->(target:Location)
OPTIONAL MATCH (warehouse)-[:HAS_RACK]->(source_rack:Rack)-[:HAS_SLOT]->(source)
OPTIONAL MATCH (warehouse)-[:HAS_RACK]->(target_rack:Rack)-[:HAS_SLOT]->(target)
CALL {
  WITH task
  OPTIONAL MATCH (event:RuntimeEvent {run_id: $run_id,
                  task_id: task.task_id, type: 'boundary_port_bound'})
  WHERE event.tick <= $t
  WITH event ORDER BY event.tick DESC, event.id DESC LIMIT $binding_fetch_limit
  RETURN collect(properties(event)) AS boundary_bindings
}
RETURN requested_task_id, task IS NOT NULL AS task_exists,
       properties(task) AS task, goods.goods_id AS goods_id,
       dataset.start AS dataset_start, properties(warehouse) AS warehouse_spec,
       properties(source) AS source, properties(target) AS target,
       properties(source_rack) AS source_rack, properties(target_rack) AS target_rack,
       physical_ports, boundary_bindings
```

**存在理由：**任务截止时间和地面坐标都无法代替机械臂取放要求；高层取货与高层放货对接力的要求不同。

- 批量参数 `task_ids` 仅来自已观察候选、本机任务或明确接力请求，去重后最多32项。返回静态定义不代表任务已释放或可领取。
- `source/target` 返回 `kind/level/face/bay/rack_id/x/y` 等真实字段。`dataset_start` 用于将任务 ISO 时间换算为运行秒；期限余量为 `due_second - basis.step.elapsed`，不能拿 tick 直接减 ISO 时间。
- 货位要求复用 `backend/wide/capabilities.py` 的 `slot_requirement()`；型号限制复用 `access_reason()`，不要在 Cypher 中再维护 A1/R2/X3 的第二套常量。完整任务检查源与目标；只有已确认取货/交接、正在执行剩余投递时，才仅检查目标，相当于 `task_capability_reason(..., remaining=True)`。
- 逻辑 `INBOUND/OUTBOUND` 不是实际坐标。解析绑定事件的 `details_json` 或 `payload`，按 `endpoint` 找 `actual_id`，再从 `physical_ports` 取坐标；没有有效绑定时返回 `needs_port_selection`。不能用 `(0,0)` 兜底。
- `binding_fetch_limit=17` 表示最多展示16条并用第17条识别截断；缺绑定、截断无法确认最新端点、同 tick 冲突，均保留未知。无 APOC 依赖，JSON 解析放在组装器。
- 当前静态导入存在 Rack ID 与 `Location.rack_node_id` 不一致的问题，`HAS_SLOT` 可能缺失。查询保留 `source_rack/target_rack=null`，不能把缺少货架记录解释成伸展要求为0；可用与 `scene_sha256` 匹配的布局缓存补充，否则能力结论为未知。本次不修改导入逻辑。

例如：A1 不能承接“尚未取下的 L3 出库货物”；已由长臂取下且确认交接后，若剩余目标是地面出库口，A1 可通过剩余机械臂要求检查。L3 入库任务的目标仍在高层，接力不会消除这个要求。

### `task_evidence`：任务执行与交接证据

回答：任务有没有被执行、重新排队或交接？目前有哪些归属和载货证据？

触发：接单前查少量候选；取货/放货/交接前查相关任务；恢复时查本机未完成任务。

参数示例：

```json
{
  "run_id": "YOUR_RUN_ID",
  "dataset_id": "ANCHOR_DATASET_ID",
  "t": 100,
  "task_ids": [
    "KNOWN_TASK_ID"
  ],
  "evidence_fetch_limit": 17
}
```

```cypher
MATCH (:Run {id: $run_id})-[:USES_DATASET]->(dataset:Dataset {id: $dataset_id})
UNWIND $task_ids AS requested_task_id
OPTIONAL MATCH (dataset)-[:INCLUDES_TASK]->(task:WarehouseTask {task_id: requested_task_id})
CALL {
  WITH task
  OPTIONAL MATCH (state:ExecutionState {run_id: $run_id, task_id: task.task_id})
  WHERE state.tick <= $t
  WITH state ORDER BY state.tick DESC, state.id DESC LIMIT 1
  RETURN properties(state) AS execution_sample
}
CALL {
  WITH task
  OPTIONAL MATCH (change:OwnershipChange {run_id: $run_id, task_id: task.task_id})
  WHERE change.tick <= $t
  WITH change ORDER BY change.tick DESC, change.id DESC LIMIT $evidence_fetch_limit
  RETURN collect(properties(change)) AS ownership_changes
}
CALL {
  WITH task
  OPTIONAL MATCH (handoff:Handoff {run_id: $run_id, task_id: task.task_id})
  WHERE handoff.tick <= $t
  WITH handoff ORDER BY handoff.tick DESC, handoff.id DESC LIMIT $evidence_fetch_limit
  RETURN collect(properties(handoff)) AS handoffs
}
CALL {
  WITH task
  OPTIONAL MATCH (event:RuntimeEvent {run_id: $run_id, task_id: task.task_id})
  WHERE event.tick <= $t AND event.type <> 'boundary_port_bound'
  WITH event ORDER BY event.tick DESC, event.id DESC LIMIT $evidence_fetch_limit
  RETURN collect(properties(event)) AS operation_events
}
RETURN requested_task_id, task IS NOT NULL AS task_exists,
       execution_sample, ownership_changes, handoffs, operation_events
```

**存在理由：**“任务定义存在”“调度快照里出现”不能回答谁正在做；接力也不能只看一条 `ASSIGNED_TO` 关系就认定货物归属。

同时返回任务状态样本、责任变更、真实交接和操作事件。组装器识别分配、取货、完成、`task_requeued` 等证据；若较新的重新排队推翻旧分配，不得沿用旧负责人。`Handoff` 表示已发生交接，不等于某个帮助请求已被接收。

不读取可变 `Execution.current_robot_id/status` 回答过去，也不将多条 `ASSIGNED_TO` 当成同时多个负责人。`ExecutionState.status` 可能是动作阶段，不能仅按“不是 completed”推导可领取。

每组最多显示16条，用第17条标记截断；`execution_sample` 返回样本 tick，不能默认等于 t。同 tick 多个互相矛盾的变更不能靠字符串 ID 排序认定先后；若无可靠业务序号则输出 `conflict/unknown`。没有证据不等于“任务无人认领”，近期证据也不代替动作前的原子认领及当前货物持有验证。

### `peer_states`：同伴状态与接力候选依据

回答：哪些同伴值得进一步联系或避让？谁可能接走已取下的货？

触发：发生求助、准备接力，或需要周边态势时；同一 t 的同伴读取可在机器人之间共享。

参数示例：

```json
{
  "run_id": "YOUR_RUN_ID",
  "robot_id": 1,
  "t": 100,
  "max_peer_age_ticks": 4
}
```

```cypher
MATCH (:Run {id: $run_id})
MATCH (robot:Robot {run_id: $run_id})
WHERE robot.robot_id <> $robot_id
CALL {
  WITH robot
  OPTIONAL MATCH (state:AgentState {run_id: $run_id, robot_node_id: robot.id})
  WHERE state.tick <= $t
  WITH state ORDER BY state.tick DESC, state.id DESC LIMIT 1
  RETURN state{.tick, .stage, .battery, .x, .y, .task_id, .cargo_id} AS state
}
RETURN robot.robot_id AS robot_id, robot.type AS robot_type, state,
       $t - state.tick AS age_ticks,
       CASE WHEN state IS NOT NULL AND $t - state.tick <= $max_peer_age_ticks
            THEN true ELSE false END AS state_fresh
ORDER BY robot_id
```

**存在理由：**请求帮助必须知道可能的接收者；同一批位置和状态也能支持附近态势，没必要另造一条只改排序的“附近机器人查询”。

不在 Cypher 中先删掉缺状态的同伴，否则无法知道候选是否因采样缺失而消失。返回数量应与 `basis.step.expected_robot_count - 1` 对照；不足时记录机队观测缺项。

组装器先筛新鲜、字段完整、`stage=idle`、无已观察任务/货物、且不在 `task_pool.active_jobs` 的同伴，电量阈值取运行配置的 `charge_request_soc`，再用 `task_geometry` 检查剩余目标能力。按直线距离只做初筛排序，并明确标记 `distance_kind=euclidean_sort_only`。

这些是“潜在接收者”，不是已承诺助手。`AgentState` 没有完整故障、`carrying` 和助手预约字段；`cargo_id=null` 本身不能证明物理空载。最终必须由执行器确认无故障、空载、无其他工作和协助占用，并通过会合路线、交接点、投递及后续补能的时间/能源检查。也不能用点位快照代替 SIPP 的时空避碰。

### `self_feedback`：本机近期执行反馈

回答：刚才的操作有什么结果？我在等待、耗电还是持续没有进展？

触发：执行反馈到达、长时间未观察到进展、低电、补能或恢复判断时；无需每次接单都读取。

参数示例：

```json
{
  "run_id": "YOUR_RUN_ID",
  "robot_id": 1,
  "t": 100,
  "from_tick": 40,
  "state_fetch_limit": 65,
  "event_fetch_limit": 33
}
```

```cypher
MATCH (:Run {id: $run_id})
MATCH (robot:Robot {id: $run_id + ':robot:' + toString($robot_id), run_id: $run_id})
CALL {
  WITH robot
  MATCH (state:AgentState {run_id: $run_id, robot_node_id: robot.id})
  WHERE $from_tick < state.tick AND state.tick <= $t
  WITH state ORDER BY state.tick DESC, state.id DESC LIMIT $state_fetch_limit
  RETURN collect(state{.tick, .stage, .battery, .x, .y, .task_id, .cargo_id}) AS states
}
CALL {
  WITH robot
  MATCH (event:RuntimeEvent {run_id: $run_id, robot_node_id: robot.id})
  WHERE $from_tick < event.tick AND event.tick <= $t
  WITH event ORDER BY event.tick DESC, event.id DESC LIMIT $event_fetch_limit
  RETURN collect(properties(event)) AS events
}
RETURN robot.robot_id AS robot_id, $from_tick AS from_tick, $t AS through_tick,
       states, events, 'robot_node_id' AS event_scope
```

**存在理由：**只看当前状态无法知道动作是否有进展，也无法区别正常排队、补能和需要重新规划的情况。

返回窗口 `(from_tick, t]` 内的真实状态样本和本机事件，组装器按时间升序比较位置、电量与阶段，输出 `observed_movement / observed_soc_delta / recent_operation_events / sample_gap_ticks`，不把一条空事件列表解释成“没有异常”。

示例最多显示64条状态、32条事件，分别取65/33识别截断；两组独立标记，不将截断窗口的首尾差称为完整窗口统计。状态数量不是持续时长；tick 与秒的映射没有确认时，不输出每秒耗电率。

只观察到位置不变，不能直接认定故障：正常取放、排队、充电和换电也可能静止。这里只读取写者明确关联 `robot_node_id` 的事件；不关联本机的全局事件不在此范围，相关任务交接等通过 `task_evidence` 补充。没有补能事件也不证明没有补能。

## 按操作组包，不是每次执行全部查询

| 待做操作 | 使用哪些模板 | 还需即时确认 |
|---|---|---|
| 接新任务 | `basis → task_pool → task_geometry + task_evidence` | 任务原子认领、实时库存/货位、路径与能源可行性 |
| 去取货、取货 | `basis → task_geometry + task_evidence` | 真实物理源点、源库存、货位预约、机械臂能力、通路 |
| 去放货、放货 | `basis → task_geometry + task_evidence` | 本机确实持有此货、目标可接纳、目标预约、通路 |
| 请求/提供接力 | `basis → task_evidence + task_geometry + peer_states` | 有效协助请求和承诺、空载/无故障、会合点、双方资源预约 |
| 判断是否补能 | `basis`，需要解释变化时加 `self_feedback` | 真实补能点、电池与队列、可达路径、完成任务后的保底电量 |
| 执行反馈/恢复 | `basis → self_feedback`，涉及任务时加 `task_evidence` | 当前执行器、故障原因、恢复动作有效性 |

`task_geometry` 和 `task_evidence` 可批量查少量任务；同一组包内相同查询只执行一次。按需读取与缓存属于调用层工作，不额外增加语义重复的查询。

组装后的候选应包含 `task_id / proposed_action / physical_target / capability_result / deadline_slack_seconds / evidence_ids / unknown_preconditions`。直线距离只能是排序提示；真正的 ETA、SOC 成本和可达性由当前道路模型、SIPP、时空预约及能耗规则计算，不能复制 LaDe 的直飞距离公式。电量采用本项目的 SOC 百分比。

例如 A1 接收一件已被长臂取下的 L3 出库货物：`task_evidence` 先提供已取货和实际交接证据，`task_geometry` 再检查剩余地面目标。只有“可以考虑接力”，仍缺实时请求承诺/会合预约时，应返回 `unknown_preconditions`，不能输出可执行交接指令。

## 必须补的数据：暂不伪造可运行查询

下面不是为了扩充目录，而是现有六条无法回答、相应动作又确实必须知道的信息。当前 C 图缺少完整事实，只有接口契约；不能将拟议节点当作现存数据直接发 Cypher。

| 必须回答的问题 | 何时需要 | 权威来源与最小补充契约 | 缺少时如何处理 |
|---|---|---|---|
| 货物现在在哪、目标货位是否可用 | 取货/放货 | `sim.goods/slots`：按 Run 和已发布版本保存货物位置/持有人、货位占用及预约；需要变更版本与原子校验 | `INITIAL_AT` 只代表初始库存；不得据此抓货或宣称目标空闲 |
| 下一段路能否走、何时可通过 | 导航/避让/接力会合 | 当前 roadmap、障碍、SIPP reservations：路段/节点/方向、占用时间区间、机器人、资源版本；规划服务基于同版本输出路线证据与能耗 | `DispatchState.reservations_json` 只有汇总；不能据它做避碰。查询可读预约，完整搜索仍由算法完成 |
| 去哪里补能，预计等多久 | 充电/换电 | `scene.docks/homes`、`BatteryPool`、作业队列：物理点规范 ID、别名、服务类型、运行启用范围、可用时刻、可用/已预约电池、队列和资源版本 | 当前静态导入只覆盖任务位置及逻辑边界；布局中的100个泊位不等于100个换电站。无数据不能声称可到达或有电池 |
| 谁已请求/承诺接力，交接点是否已预约 | 请求帮助/接收帮助/交接 | `sim.assists/jobs/handoff_ready/faults`：请求 ID、状态版本、双方、任务/货物、有效期、会合点/时段、承诺和取消记录 | 当前 `Assist` 是可变汇总，不能可靠回溯历史活跃请求；`Handoff` 是已发生交接，不是未来承诺 |

这些契约需要与全局写入和 Step 发布一起设计。补完后才增加相应读取模板；不能通过机器人每次解析整份 `WarehouseLiveCheckpoint` 来掩盖缺失，也不能把未来缺项静默改成默认可用。完整自主控制还需要可拒绝、可重试的原子认领/预约/释放协议。
