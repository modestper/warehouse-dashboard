# 快速闭环任务集界面变化慢排查

### 任务背景

用户在前端执行“快速闭环任务集”，等待较长时间后仍觉得 UI 没有明显变化。本次只读检查本机 4173 服务快照、任务输入和释放逻辑，保留正在运行的现场，没有重启、暂停、修改倍速或另开运行。

### 关键结论

- 已查明直接原因：当前任务集是 `sample19`，共有 19 单，释放时间分布在约 30 分钟内；首单要到仿真第 **208 秒（3分28秒）** 才释放。
- 当前倍速为 **1.0**，实测约 0.99～1.00 倍，因此刚开始需要现实等待约 3分半，才会看到业务机器人开始出发。
- 第一次观测时仿真时间为 148 秒，19 单均未释放，20 台充电、80 台待命，没有正在执行的配送任务，地图自然几乎不变。
- 两次快照间墙钟过去 27.359 秒，仿真时间从 148 推进到 175 秒，说明后端持续推进。
- 随后实际观察到首单在 208 秒释放、210 秒分配给 37 号机器人；第二单在 221 秒释放、230 秒分配给 8 号机器人。最新采样为 238 秒，两台均处于 `to_source`，确认任务释放和派发已生效。
- 观测中运行状态始终为 `running`，`lastError=null`，图谱错误和规划失败均为 0。此次现象主要由稀疏的任务时间表和“快速闭环”名称容易让人期待立即有任务造成；本次没有证据表明后端卡住。
- 可用前端倍速控件提高请求速度，如 5 倍或 10 倍，不必为了加速重新创建 run；实际速度仍取决于图谱和仿真处理能力。

#### 前几单的释放时间

任务 CSV 以 `2026-10-27T00:00:00+08:00` 为输入起点，运行器将其转换成相对仿真秒数；不是等待系统实际日期到达该历史时间。

| 任务 | 类型 | 仿真释放时间 |
|---|---|---|
| `V3-T-0000013` | 出库 | 03:28（208秒） |
| `V3-T-0000012` | 入库 | 03:41（221秒） |
| `V3-T-0000008` | 入库 | 04:46（286秒） |

| `V3-T-0000007` | 出库 | 09:13（553秒） |

最后一单在 29:59（1799秒）才释放。任务全部完成还需要这之后的运输与处理时间，不能将“30分钟输入窗口”解释为“30分钟内已经完成全部配送”。

首单的已观测事件链：

```text
tick 208  task_released  V3-T-0000013
tick 210  task_assigned  robot_id=37
tick 221  task_released  V3-T-0000012
tick 221  received       V3-T-0000012 / IN-2
```

释放与派单时间略有差异是因为默认每 10 秒进入一轮匹配。第 208 秒释放的首单，在下一轮第 210 秒派发。

### 执行过的操作

- 阅读 `config/live-datasets.json`，定位“快速闭环”对应的 `sample19` 注册项。
- 用 `./run_in_lade.sh python -c '…'` 只读解析 `data/examples/warehouse-v5/manifest.json`、`tasks.csv`，计算任务释放时刻。
- 读取 `backend/scheduling_v2/sim.py` 的默认10秒派单周期，以及 `backend/scheduling_v5/sim.py:release_and_dispatch()`。
- 读取 `ops/warehouse_live_runtime.py:_worker()`、`ops/start_neo4j_live.py` 和前端时钟、未发布任务计数的实现。
- 首次沙箱内端口和本机 HTTP 读取受限；通过执行权限确认后，用 `ss -ltnp` 定位4173服务，用 `curl --noproxy '*' -fsS --max-time 10` 只读获取 `/api/snapshot`。
- 对同一 run 采集 elapsed=148、175、238 的三次快照，核对时间、计数、事件和错误字段。
- 诊断原始快照临时保存在 `/tmp/warehouse-ui-snapshot-20261104-first.json` 和 `/tmp/warehouse-ui-snapshot-20261104-a.json`。
- 没有修改运行状态、倍速、数据库、任务输入或业务代码；未运行测试，因为此次直接观测运行实例已验证释放与派单行为。
