# 逐 tick 节点生成与 10000 步控制

### 任务背景

用户希望确认当前知识图谱是否每个 tick 保存 100 个 agent 状态，以及怎样控制生成 10000 个 tick。此处 tick 指仓储仿真步，当前物理步长为 1 仿真秒。本次只读分析，没有修改启动入口、运行实验或写数据库。

### 关键结论

- 最新本地保存配置 `gaofeng1106` 使用 peak1728、record_agent_state=true、graph_state_interval=1、kg_state_source=neo4j、kg_write_mode=main、commit_seconds=5。只说明保存的运行配置，不代表本次已实时连接服务或数据库验真。
- 当前机器人图谱路径每步更新已有的 100 个 Robot 节点；开启历史且 interval=1 时，每个成功写入的 tick 另外保留 100 个 AgentState。无论机器人忙碌还是空闲都记录。
- AgentState 身份包含 runId、robotId、tick，使用 MERGE，重试同一状态不会重复新增。完整机器人回执和全局事实成功后写该 tick 的 Step 并推进 Run.latest_step；任务执行、事件、交接、统计和检查点另有节点，所以总节点数不等于 AgentState 数。
- 对 tick=1…10000，100×10000=1000000 个 AgentState。若初始 tick=0 也保存历史，会另外有初始 100 份；不同 run 的数量也需分开统计。
- 10000 tick 对应 10000 仿真秒，即 2 小时 46 分 40 秒，不是 10000 个任务，也不是固定的现实耗时。speed 只影响现实推进目标，不能绕过计算和写入等待。
- 当前 start_neo4j_live.py / warehouse_live.py 没有 max-ticks 或 until 参数。实时运行结束要求达到 manifest.duration_seconds 且全部任务完成、无未结束协作；因此任务生成时 duration_seconds=10000 不等于精确停在 tick=10000。
- 已有合成规模样本脚本支持 --robots 100 --steps 10000，但只生成 JSONL，不运行真实仿真，也不自动导入 Neo4j，不能充当真实运行产生百万状态的证据。

### 后续建议

#### 当前节点策略

| 节点 | 当前路径的记录方式 |
|---|---|
| Run | 一次运行对应身份节点，持续更新进度等信息 |
| Robot | 每机器人一个运行态节点，逐 tick 更新当前状态，不是每步新建 100 个 Robot |
| AgentState | 按 run、机器人、tick 累积历史；当前 interval=1 时每步 100 份 |
| Step | 全部机器人写入回执和全局事实完成后，按 tick 发布完整边界 |
| Execution / ExecutionState | 任务执行身份及执行历史，数量随任务/执行状态而变化 |
| RuntimeEvent / Handoff / OwnershipChange | 按业务事件和交接事实生成，不要求每步固定 100 条 |
| RunStat / DispatchState | 全局统计、调度记录，按对应 writer 的节奏保存 |
| WarehouseLiveCheckpoint / WarehouseLiveCommit | 最新检查点及提交批次；commit_seconds=5 与 AgentState 的逐步采样不同 |

AgentState 采样条件为：

```python
record_agent_state and (tick % state_interval_ticks == 0 or tick == 1)
```

因此间隔 4 时只存对应采样步，并另保留 tick=1；不是每推进一步都新增 100 份历史。为获得逐步历史，应显式传 `--record-agent-state --graph-state-interval 1`。

#### 如果目标是实际运行积累至少一百万份状态

沿用现有有效 Neo4j 连接配置，以新的 runId 使用全天 day 输入或其他运行时长至少 10000 秒的输入。例如：

```bash
./run_in_lade.sh python ops/start_neo4j_live.py \
  --dataset-id day \
  --run-id million-states-20261109 \
  --record-agent-state \
  --graph-state-interval 1 \
  --speed 10 \
  --port 14583
```

此命令是供用户参考，没有执行。端口必须空闲，连接环境、实际数据库名及密码需要已有正确配置。day 输入的 manifest 为 86400 秒，因此不会像短高峰输入那样可能在不足 10000 tick 时完成停止。实际仍须没有运行或写库失败；speed=10 是目标倍速而不是吞吐保证。

当图谱完整水位达到 10000 后，tick=1…10000 这一段理论上有 100 万 AgentState。后台继续运行时总量还会增长，不能依靠浏览器轮询后点击暂停保证恰好停止在 10000。

只读核对进度：

```cypher
MATCH (r:Run {id: 'million-states-20261109'})
RETURN r.latest_step AS latest_complete_tick;
```

核对目标区间历史状态：

```cypher
MATCH (s:AgentState {run_id: 'million-states-20261109'})
WHERE s.tick >= 1 AND s.tick <= 10000
RETURN count(s) AS agent_states,
       count(DISTINCT s.tick) AS recorded_ticks,
       count(DISTINCT s.robot_id) AS robots;
```

预期为 1000000、10000、100。若要验证每一步都完整，可按 tick 分组检查：

```cypher
MATCH (s:AgentState {run_id: 'million-states-20261109'})
WHERE s.tick >= 1 AND s.tick <= 10000
WITH s.tick AS tick, count(DISTINCT s.robot_id) AS robots
RETURN count(*) AS ticks, min(robots) AS min_robots, max(robots) AS max_robots;
```

还需结合 recorded_ticks=10000，避免把缺失整步漏查成通过。上述查询只读，但大规模计数仍有开销，无需高频轮询。

#### 如果要求精确自动停在 10000

当前 realtime 启动入口没有这个功能。合适的后续改动是在实时 owner 每步完成、图谱确认和必要持久化后检查 tick 上限，达到时自动暂停并保存，不丢弃原有运行。需同步接通启动器、运行器和新 run 生命周期；本次仅说明现状，没有自行实现。

现有其他入口的区别：

- `backend.warehouse run --until 10000 --window` 可以限定批处理到仿真秒 10000；必须配合 --window，否则 until 后仍可能排空任务。它使用 journal/旧镜像提交路径，不应当作当前 Neo4j 无 journal 实时 actor 路径的同义替换。其可选 C 图谱写入发生在 persist 时，单设 state_interval_ticks=1 而 commit_seconds>1 并不能让未发布的中间 tick 自动出现。
- `ops/kg_long_run.py run --max-ticks 10000` 的确逐步调用现有机器人 actor 引擎，但属于专门实验入口，要求全天输入、wheeled 配置、HTTP global writer 等条件，runId 还必须以 wz-test- 开头。不是直接加给 start_neo4j_live.py 的参数，本次不建议无视条件照搬。若要保留图谱，不能启用它的 --cleanup。
- 当前 live 控制 API 支持 ready/paused 状态下单步 action=step，理论上可以逐次推进并在目标 tick 停下；每次单步强制持久化，重复 10000 次并非合适的高吞吐方案。

#### 如果只是生成一百万条合成状态文件

```bash
./run_in_lade.sh python scripts/generate_million_runtime_dataset.py \
  --robots 100 --steps 10000 \
  --output data/generated/scale-100x10000-20261109 \
  --write
```

生成范围是 tick=0…9999，共 10000 个采样 tick，输出 agent_states.jsonl 和 runtime_events.jsonl。它与真实仿真推进 tick=1…10000 是两种不同编号区间。脚本不会自己向 Neo4j 导入；应使用全新输出目录，避免覆写先前 JSONL。本次没有执行 --write。
